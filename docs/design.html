◣ Trireme

A non-interactive agentic harness that builds a Node package from a specification and a robust acceptance suite — and stops on an objective verdict, a cost cap, or a clock.

Design v0 · draft for review 2026-08-15 node 24.19.0 · pnpm 11.22.0 · pi 0.84.2
At a glance

Everything below follows from decisions already made. This section is the summary; the rest is the detail you'd need to author a job or review the implementation.

Job format

What you author

A job is a directory. Nothing in it is generated; all four parts are written by a human (or by an upstream process) and are read-only to the agent.

my-job/
  trireme.json        manifest — identity, model, limits
  spec.md             structured prose — the authority on behaviour
  contract.d.ts       TypeScript declarations — the authority on shape
  acceptance/
    *.test.ts         vitest — the authority on done

trireme.json

{
  "name": "semver-lite",
  "version": "0.1.0",
  "description": "Parse, compare, and sort semantic versions.",

  "model": "anthropic/claude-opus-5",   provider/id, as pi resolves it
  "thinking": "high",                  off|minimal|low|medium|high|xhigh|max

  "limits": {                         budgets — hitting one is a normal outcome
    "costUsd": 5.00,
    "wallClockMinutes": 30
  },
  "safety": {                         pathology detector — hitting one means something is wrong
    "maxIterations": 100
  },

  "dependencies": {},                 v1: empty. See “Dependencies”.

  "paths": {                          optional; these are the defaults
    "spec": "spec.md",
    "contract": "contract.d.ts",
    "acceptance": "acceptance"
  }
}

Every limits field and both model fields can be overridden per run from the CLI, so a manifest is a set of defaults, not a cage.

Why two blocks

Cost and wall clock are budgets: hitting one means the job was too expensive for its allowance, which is ordinary information. maxIterations is a safety net: tripping it while still under budget means the loop is thrashing cheaply, which is a defect. Different meanings, so a different block, a default high enough that tripping it is genuinely anomalous, and its own outcome class.

spec.md — required sections

The harness validates that these H2 headings exist and are non-empty; a job missing one never starts. The list is deliberately short — it fixes where to look, not how much to write.

SectionCarries
## PurposeWhat the package is for, in a paragraph. Orientation, not requirements.
## Public APIEach export in prose: what it does, what it returns, what it throws. The contract fixes the shape; this fixes the meaning.
## BehaviorThe rules, including edge cases and error conditions. The substance of the spec.
## ConstraintsInvariants that hold across the API — input immutability, complexity bounds, determinism.
## Non-goalsExplicitly out of scope, so the agent doesn't build it.
## ExamplesOptional. Illustrative usage; not a substitute for the acceptance suite.

The contract, and how conformance is checked

contract.d.ts declares the public API exactly. The harness generates a conformance module that asserts assignability in both directions — the implementation provides everything the contract declares, and exports nothing beyond it. It is typechecked, never executed.

// .trireme/conformance.ts — generated, sketch
import * as Impl from "../src/index.js";
import type * as Contract from "#contract";

declare const asContract: typeof Contract;

const _implProvidesContract: typeof Contract = Impl;
const _implAddsNothing: typeof Impl = asContract;

This is what makes an API-shape mistake a compile error rather than a mystery test failure — cheaper, and it lands before any test runs.

How acceptance tests reach the package

They import it by its package name, exactly as a real consumer would: import { parse } from "semver-lite". Node's self-reference resolution handles it via the generated exports field, so the tests exercise the real public entry point and never reach into src/.

The run

What the harness does

01Validate — manifest, spec sections, contract parses, acceptance suite present. Failure here is error:usage and costs nothing.
02Scaffold — generate the workspace deterministically and copy in the job's read-only files.
03Open session — one pi session, typed tools registered, pi's built-ins withheld. System prompt carries the method; the first message carries spec, contract, and the acceptance file list.
04Turn — the agent works until it ends its turn. Cost is metered per assistant message.
05Gate — the harness runs the acceptance suite and the typecheck itself. The agent is never asked whether it is finished.
↺Not green, limits intact → re-prompt with the structured failures and return to 04.
06Build & pack — tsc to dist/, write the publishable manifest, pack a tarball.
07Report — outcome class, ledger, artifacts. Written on every path, including failure and abort.

Workspace — what the agent sees

workspace/
  package.json            generated · locked
  tsconfig.json           generated · locked
  vitest.config.ts        generated · locked
  .trireme/conformance.ts generated · locked
  contract.d.ts           from job   · read-only
  acceptance/*.test.ts    from job   · read-only
  src/
    index.ts              agent — the public entry point
    modules/<name>/       agent — implementation + its own tests

Read-only is structural, not policed: no tool takes a path, and no target addresses the locked or job-owned files for writing.

Run directory — what you get afterwards

runs/<utc-timestamp>-<hash>/
  config.resolved.json    manifest after CLI overrides
  workspace/              kept on every outcome
  sessions/main.jsonl     pi transcript (a tree, once sub-agents exist)
  events.jsonl            harness log: tool calls, test runs, ledger ticks
  report.json             structured verdict
  report.md               the same, readable
  artifact/<name>-<ver>.tgz
Agent interface

Eight typed tools

No path is ever a string the agent composes. Every tool addresses a target, and the harness maps targets to paths — which is what makes the invariants hold by construction and gives the harness a live model of the build rather than a directory listing.

ToolShapeNotes
read{ target }Any target, including the read-only ones. Returns numbered lines.
list_modules{}The build graph: each module's purpose, files, whether it has tests, last test status.
declare_module{ name, purpose }Creates the directory and registers the module. Purpose is recorded for the report.
write{ target, content }Writable targets only.
edit{ target, find, replace, replaceAll? }The primary mutation. Output tokens are the expensive ones; whole-file rewrites are the thing to avoid.
remove{ target }Restructuring is real; deletion shouldn't require a workaround.
run_tests{ scope }acceptance · module <name> · all. Structured results, not stdout.
typecheck{}tsc over source, acceptance, and the conformance module. Structured diagnostics.

Targets

TargetResolves toAccess
{ kind: "spec" }spec.mdread
{ kind: "contract" }contract.d.tsread
{ kind: "acceptance", file? }acceptance/…read
{ kind: "entry" }src/index.tsread · write
{ kind: "module", name, file? }src/modules/<name>/<file⎮index.ts>read · write

A module is a directory, not a file — internal structure is the agent's to choose. Its tests are simply files matching *.test.ts inside it, which is what run_tests scopes to.

Method, stated in the system prompt

Work module by module. For each: declare it, write its exported types
and its tests, run them and watch them fail, then implement until they
pass. Move to the next only when the current one is green.

The acceptance suite is the goal and is not yours to edit. Your own
module tests are scaffolding — they help you build, and they do not
decide whether the job is done.

Read the spec before writing code, and re-read it when a test disagrees
with you. The contract fixes the shape of the public API; the spec fixes
its meaning.

The same expectation is repeated in the tool descriptions, so the method travels with the tools. Stated calmly and once — an over-emphatic prompt reliably makes current models worse, not more compliant.

Deliberate omission

There is no done tool. The agent cannot declare victory; the harness runs the gate. This is the single most important property of the loop, and it's cheapest to get right by never building the affordance.

Verdict

Done, failed, aborted

Done means all three: every acceptance test passes, tsc reports no errors across source, acceptance and conformance, and the package builds. Nothing else is in the gate.

OutcomeExitMeaningA campaign should
success0Gate passed; tarball written.continue
failed:cost_cap1Budget exhausted, tests still red.continue
failed:wall_clock1Time cap hit, tests still red.continue
failed:no_progress1Three consecutive turns with no mutating tool call while still red.continue
failed:iteration_cap1Safety net tripped: the loop kept turning without converging or exhausting a budget.continue
aborted:infra2Provider outage, exhausted usage limits, auth or network failure — after pi's own retries.stop
error:usage3Malformed job or flags. Never started.stop and fix

Where causes overlap — a run near its cap when the provider fails — aborted:infra wins, because it is the class that halts a campaign and that is the safe direction to err in. Artifacts are written on every path; a run that died mid-flight still tells you how far it got.

The ledger

The subscription bills nothing per token, so cost is imputed: tokens × published list price, taken from pi's own model registry, split across input, output, cache-read and cache-write. Budgets are therefore denominated in list-price dollars, and the report states that plainly so the number is never mistaken for an invoice.

Both limits are checked after every assistant message, so overshoot is bounded by one message. Wall clock starts when the process starts and includes scaffolding and installs — the honest reading of the phrase. Time lost to provider backoff counts against it, and is also recorded separately so a stalled run is legible as such.

Dependencies

Zero by default, artifacts when needed

The package under construction has no runtime dependencies, and no tool exists for the agent to add one. What the manifest may declare is a different thing: dependencies the harness installs before the agent starts, from two sources.

  • Registry — an allowlist, installed by the harness. The agent never sees a network.
  • Local artifact — a tarball produced by an earlier trireme run, pinned by name, version and run id.

These are one mechanism, because the successful output of a run is an npm-packable tarball and both package managers install from a tarball path natively. That is also what makes the dogfooding milestone reachable: trireme's own shell becomes a job that depends on artifacts trireme produced.

v1 constraints: artifacts are immutable, a job whose dependency artifact is missing does not start, and ordering is the caller's problem until a campaign runner exists.

Internals

A pure core and a thin shell

Trireme is one package — exports for the library, bin for the CLI — organised internally as ES modules. Nothing becomes its own package until it earns one. The split below is not architecture for its own sake: the pure column is exactly the set of modules that can later be promoted, mechanically, into trireme jobs.

How the shell gets an objective verdict too

Every impure module takes its effect as an injected input, so its acceptance tests are deterministic. The session driver is the interesting case: pi supports a streamFn that returns a scripted event stream — its own test suite uses exactly this to drive the agent loop with no model. Budget exhaustion, wall-clock expiry, no-progress and infra aborts are therefore all testable offline, in milliseconds, for nothing.

Trireme is built the way trireme builds: spec, contract and acceptance suite first, then implementation until green. Its acceptance suite is the artifact worth your attention — reviewing it is how you review the project.

Milestones

Order of work

M0Contract — trireme's own spec.md, index.d.ts and acceptance suite, plus the sample job. You review the suite before implementation starts.
M1Green — pure core, then shell, then the loop. Ends when trireme builds the sample job end to end against a real model.
M2Dogfood — promote pure-core modules to jobs and have trireme rebuild them. This is both the real end-to-end test and a natural source of further rungs.
M3+Later — campaign runner, sub-agent delegation, registry publishing. Deliberately out of scope now; the ledger tree, test scoping and tool scoping already anticipate them.
Benchmark

A ladder, not a smoke test

Live runs are not there to verify correctness — the module suites and the scripted-agent pipeline test already do that, deterministically and for free. Live runs measure something else: how far trireme gets as a machine that turns a problem statement into a working package. So they belong in a benchmark that grows over time, where each new rung is expected to strain the harness somewhere and thereby tell us what to build next.

Three test surfaces, three different claims

SurfaceAgentProvesCost
Module acceptancenone — effects injectedEach module does what its contract says.free · ms
Pipeline playbackscripted streamFnThe machine works end to end, including every failure path.free · seconds
Benchmark runga real modelThe actual claim — and where the harness strains.real

The first two run on every change. The third is invoked deliberately, and is the only surface that can reveal a model fighting the tool surface rather than using it.

The axes a rung can vary

Difficulty is not a scalar. A large-but-easy package and a small-but-hard one break completely different parts of the harness, which is what makes this a ladder rather than a pile.

Rung 1 — semver-lite

Parse, compare and sort semantic versions, plus a small range subset. Pure, zero-dependency, unambiguous, rich in edge cases — prerelease ordering, build metadata, numeric versus lexical identifier comparison. Small enough to run often, nasty enough that a weak implementation fails honestly. It anchors the simple end and nothing more.

Authoring cost, and the way around it

Rungs get more expensive to write as they get harder, because the acceptance suite is the load-bearing assumption and a robust suite for a complex package is harder to write than the package. The way through is to derive rungs from standards that already ship conformance corpora — semver's published vectors, RFC 4180 for CSV, RFC 6901/6902 for JSON Pointer and Patch, the well-known glob and diff suites. A rung built on a standard gets a high-quality suite nearly free, and “does it conform to the RFC” is exactly the kind of verdict this harness is built to render.

What this requires of the report, today

Comparison only works if every run emits the same record, so report.json carries not just the outcome and the ledger but full provenance: trireme version, system-prompt hash, model, thinking level, job hash. Without it the numbers stop being comparable the moment the prompt changes — and the most valuable comparisons are precisely the ones across harness versions. This is free now and awkward to retrofit.

It also gives the deferred campaign runner a concrete purpose: run rung R, N times, across M models, and emit the table. Run-to-run variance is a first-class measurement, not a nuisance.
